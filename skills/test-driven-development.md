# Test-Driven Development — 测试驱动开发

## 铁律

```
没有先写失败测试，就不能写生产代码。
```

**核心原则：** 如果你没有看到测试失败，你就不知道它是否测试了正确的东西。

## 红-绿-重构循环

### 红 (RED) — 写失败测试

写一个展示应该发生什么的最简测试。

**要求：**
- 一个行为
- 清晰的测试名称（描述行为，不是"test1"）
- 使用真实代码（除非不可避免，否则不使用 mock）

### 验证红 — 观察失败（**必须，不能跳过**）

```bash
# 运行测试，确认：
# - 测试失败（不是报错）
# - 失败信息符合预期
# - 因功能缺失而失败（不是因为拼写错误）
```

**测试通过了？** 你在测试已有行为。修复测试。

### 绿 (GREEN) — 最小代码

写最简代码让测试通过。

- 不要添加功能
- 不要重构其他代码
- 不要"改进"测试范围之外的内容

### 验证绿 — 观察通过（**必须**）

```bash
# 运行测试，确认：
# - 测试通过
# - 其他测试仍然通过
# - 输出干净（无错误、无警告）
```

### 重构 (REFACTOR) — 清理

仅在绿色之后：
- 消除重复
- 改进命名
- 提取辅助函数

保持测试绿色。不要添加行为。

## 为什么顺序很重要

**"我会在之后写测试来验证"**
- 事后写的测试立即通过，什么也证明不了
- 先写测试强迫你看到测试失败，证明它确实在测试某些东西

**"已经手动测试了所有边缘情况"**
- 手动测试是临时的，无法重复运行
- 自动化测试每次都以相同方式运行

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| "太简单了，不需要测试" | 简单代码会损坏。写测试只需 30 秒。 |
| "我会之后测试" | 立即通过的测试什么也证明不了。 |
| "已经手动测试了" | 临时的 ≠ 系统性的。无记录，无法重新运行。 |
| "删除 X 小时的工作是浪费" | 沉没成本谬误。没有真实测试的代码是技术债务。 |
| "TDD 会让我变慢" | TDD 比调试更快。务实 = 先写测试。 |

## 红色警报 — 停止并重新开始

- 代码写在测试之前
- 实现后才写测试
- 测试立即通过
- 无法解释测试为什么失败
- 为"之后"留下测试
- 合理化"就这一次"

**所有这些都意味着：删除代码。用 TDD 重新开始。**

## 验证清单（完成前）

- [ ] 每个新函数/方法都有测试
- [ ] 在实现之前观察到每个测试失败
- [ ] 每个测试以预期原因失败（功能缺失，而非拼写错误）
- [ ] 写了最小代码通过每个测试
- [ ] 所有测试通过
- [ ] 输出干净（无错误、无警告）
- [ ] 测试使用真实代码（仅在不可避免时使用 mock）
- [ ] 边缘情况和错误已覆盖
