# Verification Before Completion — 完成前验证

## 铁律

```
没有新鲜的验证证据，不得声明任何完成状态。
```

在没有验证的情况下声明工作已完成是不诚实，而不是高效。

**核心原则：** 证据先于声明，永远如此。

## 门控函数

在声明任何状态或表达满意之前：

1. **识别**：什么命令能证明这个声明？
2. **运行**：执行完整命令（新鲜的、完整的）
3. **阅读**：完整输出，检查退出代码，统计失败数
4. **验证**：输出是否确认声明？
   - 如果否：用证据说明实际状态
   - 如果是：用证据说明声明
5. **然后**：做出声明

跳过任何步骤 = 说谎，而不是验证

## 常见失败

| 声明 | 需要 | 不充分 |
|------|------|--------|
| 测试通过 | 测试命令输出：0 个失败 | 上次运行，"应该通过" |
| 代码检查干净 | 检查器输出：0 个错误 | 部分检查，外推 |
| 构建成功 | 构建命令：退出代码 0 | 检查器通过，日志看起来不错 |
| Bug 已修复 | 测试原始症状：通过 | 代码已更改，假定已修复 |
| 需求已满足 | 逐行核对清单 | 测试通过 |

## 红色警报 — 立即停止

- 使用"应该"、"可能"、"似乎"
- 在验证之前表达满意（"太好了！"、"完美！"、"完成！"等）
- 即将提交/推送/PR 而没有验证
- 信任 agent 的成功报告
- 依赖部分验证

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] "所有测试通过"
❌ "现在应该通过了" / "看起来正确"
```

**构建：**
```
✅ [运行构建] [看到：退出代码 0] "构建通过"
❌ "检查器通过了"（检查器不检查编译）
```

**需求：**
```
✅ 重新阅读计划 → 创建清单 → 逐一验证 → 报告差距或完成情况
❌ "测试通过，阶段完成"
```

## 合理化预防

| 借口 | 现实 |
|------|------|
| "现在应该能工作" | 运行验证 |
| "我很有把握" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "代码检查通过了" | 代码检查 ≠ 编译器 |
| "太累了" | 疲劳 ≠ 借口 |

## 底线

**不要在验证上走捷径。**

运行命令。阅读输出。然后声明结果。

这是不可谈判的。
