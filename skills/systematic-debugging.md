# Systematic Debugging — 系统化调试

## 铁律

```
在找到根本原因之前，不得尝试任何修复。
```

随机修复会浪费时间并产生新的 Bug。快速补丁会掩盖根本问题。

## 四个阶段（必须按顺序完成）

### 阶段一：根本原因调查（在尝试任何修复之前）

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 完整阅读堆栈跟踪
   - 注意行号、文件路径、错误代码

2. **稳定复现**
   - 能可靠地触发吗？
   - 确切的步骤是什么？
   - 如果无法复现 → 收集更多数据，不要猜测

3. **检查最近的变更**
   - 什么变化可能导致这个问题？
   - git diff、最近提交、新依赖、配置变更

4. **在多组件系统中收集证据**
   - 在每个组件边界添加诊断日志
   - 一次运行以收集证明"问题在哪里"的证据
   - 然后分析证据，找到失败的组件

5. **追踪数据流**
   - 错误值从哪里产生？
   - 谁传递了错误值？
   - 持续向上追踪，直到找到源头
   - 在源头修复，而不是在症状处修复

### 阶段二：模式分析

1. 找到正常工作的类似代码
2. 完整阅读参考实现（不要跳读）
3. 找出工作代码和损坏代码之间的差异

### 阶段三：假设与测试

1. **提出单一假设** — 明确说明："我认为 X 是根本原因，因为 Y"
2. **最小化测试** — 做最小的可能改动来测试假设
3. **一次一个变量** — 不要同时修复多个东西

### 阶段四：实现修复

1. **创建失败测试用例** — 最简单的复现，自动化测试优先
2. **实现单一修复** — 解决已识别的根本原因
3. **验证修复** — 测试通过？没有其他测试损坏？

**如果修复无效：**
- 停止
- 如果尝试修复次数 < 3：回到阶段一，用新信息重新分析
- **如果 ≥ 3 次修复失败：停止并质疑架构** — 不要尝试第 4 次修复

## 红色警报 — 立即停止

如果你发现自己这样想：
- "先快速修复，之后再调查"
- "就试试改一下 X 看看是否有效"
- "可能是 X，让我修复它"
- "我不完全理解，但这可能有效"
- "再试一次修复"（在已经尝试 2+ 次之后）

**这些都意味着：停止。回到阶段一。**

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根本原因。流程对简单 Bug 很快。 |
| "紧急情况，没时间走流程" | 系统化调试比猜测尝试更快。 |
| "先试试这个，然后再调查" | 第一次修复定下了基调。一开始就做对。 |
| "我看到问题了，让我修复它" | 看到症状 ≠ 理解根本原因。 |
